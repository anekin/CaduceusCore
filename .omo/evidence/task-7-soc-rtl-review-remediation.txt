--------------------------------------------------------------------------------
EXACT FIX DESCRIPTION (rtl/soc/axi_crossbar.v)
--------------------------------------------------------------------------------
Accept is now coupled to the arbitration winner, per the plan-mandated form:

    m_awready_o[gmi] = !m_aw_active[gmi] &&
        (!m_aw_hit[gmi] ||
         (aw_grant_window[m_aw_slave[gmi]] &&
          aw_would_win[m_aw_slave[gmi]][gmi]));

and symmetrically for AR (ar_grant_window / ar_would_win).

- would_win[slave][master] is a combinational replica of the sequential
  arbitration search: for each slave it picks the first master in scan order
  (round-robin from priority+1, or fixed priority from 0 when FIXED_PRIORITY=1)
  satisfying the FULL qualifier set of the search: m_*valid_i && m_*_hit &&
  (m_*_slave == slave) && !m_*_active. Implemented via a scan-order comparison
  function is_scan_before() + per-slave qualifier vectors; the earlier-master
  mask ANDed with qualifiers must be empty for a would-win.
- Two preserved paths (Oracle R2 review requirements):
  (i)  DECERR exemption — unmapped masters keep unconditional ready (!active
       only): the `!m_aw_hit[gmi] ||` short-circuit means non-hit masters never
       enter the arbitration-window/would-win terms and never hang on unmapped
       addresses. P2/P3 checks all still PASS (log below).
  (ii) Full grant-window gating — aw_grant_window[slave] replicates the EXACT
       triple guard of the sequential search:
       !aw_busy && !s_awvalid_latched && !aw_latch_clr (symmetric for AR).
       Restricting to !busy alone would allow a ready assertion inside the
       latch-clear window, resurrecting phantom-accept by another path.
- Option (b) (DECERR-after-N-cycles for accepted-but-ungranted masters) was NOT
  implemented — explicitly forbidden by the plan.
- No combinational loop: would_win depends only on register state
  (busy/priority/active/latched/valid-latched/latch-clr) + inputs
  (valid/hit/slave/addr), never on the ready signals. The existing sequential
  grant-latch condition `if (rr_found && m_awvalid_i[gnt_val] && m_awready_o[gnt_val])`
  stays self-consistent: when the search runs, grant_window is 1 and gnt_val is
  exactly the would-win master, so ready[gnt_val] evaluates to 1 (verified in
  simulation: every grant accepted, 2,751 AW + 2,751 AR grants in P4).
- Mutation hook: new parameter `FIXED_PRIORITY` (default 1'b0 = original
  round-robin behavior; zero impact on all existing instantiations, which use
  the default). When set to 1 the sequential search scans ak=0..NUM_M-1
  (lowest index first) and the would-win replica scans from start=0, keeping
  accept coupled to the fixed-priority grant in the mutation build too.
