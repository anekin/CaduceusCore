## H4-N128-CHAIN: unsupported-documented

`_build_block` hard-clips every MMUL dimension to <=64 (`_clip_dim`, :2908-2910)
by design (it is the mini-regression builder, not a full-shape builder), so the
full 17-op chain cannot be built with the un-clipped op07 without modifying the
builder — clipping is currently the only supported chain path. This is the
formal coverage-gap record for the chain form.

HOWEVER — this todo's single-op case dispatched through the SAME firmware
command ring (IbexRunner) proves the chain infrastructure itself (doorbell ring
dispatch + firmware MMUL multi-N-tile loop + mxu_soc_wrapper N>64 store-out
path) handles N=128 correctly. The clip is a test-builder limitation, NOT a
firmware or RTL limitation. This distinction flows into todo 8's attribution.

## ISSUE-13B FP32-dequant semantics (required reading for this evidence)

The mxu_soc_wrapper store-out dequantizes each MMUL row to FP32 whenever the
firmware programmed SCALE_ADDR (mxu_start writes it every tile,
npu_firmware.c:270; wrapper latches it at rtl/wrapper/mxu_soc_wrapper.v:229-230).
With the ones-scales this case programs, the RTL output is float32-encoded
values numerically identical to the raw INT32 manifest golden. An initial
verification pass compared the output as raw INT32 and produced a FALSE FAIL
(cos_sim=0.901548, bit_exact=False, only the golden's single nonzero row — row
16 — mismatching as FP32 bit patterns). The comparison was corrected to the
FP32 domain (same convention as _verify_attn_weight_chain's float32 readback)
and the result became cos_sim=1.000000, fp32_bit_exact=True. The false-fail
was investigated to root cause (SRAM/DRAM dumps + wrapper store-out FSM
monitor), not tolerance-fudged.
