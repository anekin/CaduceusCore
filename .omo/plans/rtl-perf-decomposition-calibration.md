**What you'll get:** 一份基于 RTL 仿真实测数据的端到端性能校准报告，覆盖 Qwen2.5-3B 的 decode TPS 和 prefill TTFT，以及 MobileNetV3/YOLOv8n/ResNet-50 的 FPS。通过分解为最小可测量"原子"再组合的方式，量化当前 RTL/firmware 的真实性能与 Func Model 架构假设之间的差距。精度目标 ±20%（基于交叉验证残差），但如果实测数据显示 firmware per-K-tile DMA loop 导致真实性能远慢于假设（PERF-09/10 数据暗示约 4.7×），则报告会如实记录这个差距而非强行拟合。

**Why this approach:** 把端到端性能分解为最小可测量的"原子"（单算子单 tile 走完整 SoC 路径的 cycle 数），在快速 RTL 仿真中测量这些原子，再用组合模型把原子拼装成端到端预测。关键发现：PERF-09/10 实测数据显示 per-tile marginal cost ~9,242 cycles/tile，远高于 Func Model 假设的 ~512 cycles/tile（raw bandwidth），原因是 firmware per-K-tile DMA loop 包含描述符获取/APB 配置/STATUS 轮询等开销。组合模型必须用实测 marginal，不能用 raw bandwidth 公式。

**What it will NOT do:** 不改 RTL 或固件代码；不跑全尺寸 MMUL SoC 仿真；不修改冻结的 Func Model 性能规格；不做 FPGA/流片级校准；不 claim `rtl_calibrated`（只 claim `rtl_calibrated_atoms`）；不强行拟合组合预测到 Func Model 数值（divergence 是校准结果，不是 bug）。

## Scope
### Must have
1. **RTL perf atom catalog** — JSON catalog of SoC-level cycle measurements for each engine op type at single-tile granularity, measured through the full SoC path (firmware doorbell → DMA → crossbar → wrapper → engine → store-out → NPU_HEAD advance). Covers MXU (single 64×64 tile, M=1/32/64 variants), SFU (6 ops: softmax/layernorm/rmsnorm/gelu/silu/rope — exp is not a standalone firmware opcode, it is part of softmax internally; measured at elements=128 AND elements=256 to span 1-batch and 2-batch points for per-batch marginal derivation), Vector (6 ops: add/mul/max_reduce/sum_reduce/conv/resid_add; measured at dim=128 AND dim=256 to span 1-batch and 2-batch points).
2. **SoC overhead atom catalog** — JSON catalog of SoC integration overhead measurements: DMA latency at multiple sizes, crossbar contention delta (sequential vs concurrent), wrapper store-out drain cycles (M-sweep), firmware dispatch latency (doorbell→CMD.START), inter-op gap.
3. **Tile scaling model** — Formula and validation for scaling single-tile SoC atoms to full-size MMUL. The model distinguishes K-tiles (weight reload required) from N-tiles (weight reuse, no reload): `full_cycles = first_tile_cold + (K_tiles - 1) × K_tile_marginal + K_tiles × (N_tiles - 1) × N_tile_compute_marginal`, where `K_tile_marginal ≈ 9,242 cyc/tile` (from PERF-09/10, N=64 fixed), `N_tile_compute_marginal ≈ 6,129 cyc/tile` (from PERF-11: N-tile strips where weights already loaded), and `first_tile_cold ≈ 11,213` (PERF-09 - 3×K_tile_marginal). Validate against PERF-09/10 (±5%, exact fit by construction) and PERF-11 (±5%, fitted point). The real blind hold-out is the M=1 single-tile atom (todo 2): direct residual gate `|atom - 11,213| / 11,213 ≤ 15%`. If residual > 15%, investigate.
4. **Composition tool** (`scripts/rtl_perf_compose.py`) — Loads atom catalogs, injects RTL-measured parameters into the existing Func Model `TimingEngine`/`NPUSimulator` pipeline, produces composed TPS/TTFT/FPS predictions with ±20% confidence bands. Does NOT modify the frozen `config/func_model_perf_spec_v1.json`; creates a separate RTL-calibrated parameter overlay.
5. **Cross-validation** — Composed predictions validated against 3 existing E2E RTL data points: (a) blk.0 17-op chain (99,565 cycles from `docs/soc-perf-report.md`), (b) MobileNetV3 52-conv RTL chain, (c) 36-layer 8-checkpoint segment run. Error quantified per-op and total.
6. **Calibration report** (`docs/rtl-perf-calibration-report.md`) — RTL-calibrated performance report with ±20% confidence bands, `calibration_state=rtl_calibrated_atoms`, per-module breakdown, and cross-validation evidence.
7. **VPlan coverage update** — E2E-07 status updated from ❌ to ✅(rtl_atom_calibrated) in `.omo/plans/soc-rtl-verification-vplan.md` with evidence links.

### Must NOT have (guardrails, anti-slop, scope boundaries)
1. **No RTL/firmware source changes** — per-tile atom strategy deliberately avoids weight-streaming firmware fixes. All measurements use existing firmware + RTL as-is. No edits to `rtl/`, `firmware/`, or `rtl/wrapper/` files.
2. **No full-size MMUL SoC simulation** — Q_proj (K=2560, N=4096, 2560 tiles) is NOT run on SoC RTL. The per-tile atom × tile_count model is the substitute.
3. **No frozen spec modification** — `config/func_model_perf_spec_v1.json` and `docs/func-model-performance-spec.md` remain frozen with `basis=architecture_assumption`. The composition tool creates a separate overlay config, not a spec revision.
4. **No FPGA/silicon calibration** — This is RTL-level atom calibration only. Silicon-level calibration remains deferred to FPGA/流片.
5. **No non-Block engine coverage** — Only Block 64×64 engine is calibrated. FSA/GMMA/TensorCore/WMMA/OS-Systolic remain deferred (same as infra-calibration-closure plan).
6. **No `calibration_state=rtl_calibrated` claim** — The state is `rtl_calibrated_atoms` (atoms measured, composition validated, but not full-E2E-RTL-calibrated). This distinction prevents overclaiming.
7. **No changes to `sim/arc_model.py`, `sim/quantize.py`, `ggml-npu/`, `requirements.txt`** — same scope guardrails as soc-rtl-verification-signoff.
8. **Hardware config scope**: Calibration is valid ONLY for Phase 1/2/3 64×64 Block engine configuration. Does not transfer to 128×128 or FSA without separate calibration.
9. **Fixed reference workloads**: Qwen2.5-3B Q4_K_M, `prompt_len=128` for decode TPS, `prompt_len=2000` for prefill TTFT, `gen_len=128`. CV models at batch=1, standard input resolution (MobileNetV3: 224×224, YOLOv8n: 640×640, ResNet-50: 224×224).
10. **Atom observation methodology**: Atoms are measured as black-box end-to-end SoC cycle deltas (doorbell→NPU_HEAD). No RTL/firmware instrumentation is added. Overhead decomposition (DMA vs crossbar vs store-out vs firmware) uses subtractive modeling: `SoC_atom - module_level_RTL = total_SoC_overhead`, then DMA/crossbar/store-out components are estimated from isolated DMA tests and M-sweep deltas, not from internal probes. If subtractive decomposition proves insufficient (residual > 15%), document as a known limitation rather than adding RTL probes.
