Agent 驱动测试方法论：testplan.md + Git 审计
来源：zartbot（渣B）公众号 + MIT HAN Lab Kernel Design Agents
版本：v1.0 | 2026-06-28
适用：任何有 Agent 参与的测试/验证项目

一、核心理念
传统测试是人写脚本、人看日志。Agent 时代应该反过来：人写规范，Agent 执行，人只看异常。

这个方法论的精髓不是工具选择，而是认知负载降维：把人的负担从 O(总测试数) 降到 O(异常数)。

二、一个文件 = 六个角色
┌─────────────────────────────────────────────┐
│              testplan.md                     │
│                                              │
│  ① 任务队列 — Agent 的 FIFO 待办清单          │
│  ② 状态看板 — 人类 3 秒判断项目健康度          │
│  ③ 共享内存 — 人机通信的唯一协议               │
│  ④ 审计日志 — git log 就是完整时间线           │
│  ⑤ 计划→执行 — 计划文件和执行记录是同一文件     │
│  ⑥ 知识沉淀 — 失败的 case 不会随测试结束消失   │
└─────────────────────────────────────────────┘
三、文件结构模板
3.1 基础模板
# [项目名] Test Plan

> 被测对象：简述被测系统
> 参考规范：列出 Agent 需要阅读的文档
> 方法论：Agent 读规范→自主生成测试→写回状态

## 验收标准

| 模块 | 指标 | 阈值 | 理由 |
|------|------|------|------|
| 模块A | 精度 | 1e-5 | 硬件精度上限 |
| 模块B | 往返误差 | 0 LSB | bit-exact 要求 |

## 优先级说明

- P0: 0% 覆盖 + 已知坑 + 下游依赖
- P1: 0% 覆盖 + bug 难排查
- P2: 有基础测试，补缺口
- P3: 大部分已覆盖，补边界
- P4: 依赖单模块先稳定

## Agent 执行规则

1. 严格按 P0→P4 顺序执行，不跳级
2. 先读被测试代码及相关规范文档
3. 每个 case：生成测试 → 运行 → 更新状态 + 结果
4. 不满足验收标准 → ❌ FAIL → 修复 → 重试（最多 3 次）
5. 3 次仍 FAIL → 保持 ❌ 等待人类介入
6. 可自主新增 case（Agent 发现未列出的方法/边界）

### Git 规则

每次 testplan.md 状态变化 = 一次 git commit

commit 格式：`[case_id] status → NEW_STATUS`

示例：
  [XX-001] ⬜ → ✅ | 具体结果描述
  [XX-002] ⬜ → ❌ | 失败原因描述
  [XX-001] ❌ → ✅ | 修复内容，重测通过

原则：
  - 每完成一个 case（无论 PASS/FAIL）立即 commit
  - 不允许批量攒多个 case 再 commit
  - 修复后重测也要单独 commit
  - git log testplan.md = 完整测试执行时间线

### 首次启动检查

Agent 在开始执行前，先执行：
  1. cd 到项目目录
  2. git status 确认状态干净
  3. 确认测试框架可用
  4. 如果 git 有未提交修改，先提交或暂存
四、Agent 输入规范
Agent 拿到以下资料就足够自主执行：

输入	作用	必须？
testplan.md	任务列表	✅
被测源码	理解接口和行为	✅
规范文档	ISA spec / microarch doc 等	推荐
已有测试（如有）	避免重复造轮子	推荐
项目 README	项目上下文	可选
不要给：预设的测试脚本、写死的测试步骤。Agent 的能力在于自主探索。

六、设计原则
6.1 表格列的选取
必选列：case_id / 优先级 / 测试目标 / 验收标准 / 状态 / 结果
可选列：方法名 / 备注 / 依赖 / 耗时

列数控制在 6-8 列，超过 8 列人类扫读效率下降。

6.2 验收标准怎么写
❌ 坏例子：精度足够 / 行为正确 / 性能达标
✅ 好例子：max_error < 1e-5 / 往返 bit-exact / 吞吐 ≥ 理论值 85%

Agent 需要可编程判断的标准，否则 PASS/FAIL 无法自动化。

6.3 优先级怎么定
P0 = 0% 覆盖 + 已知错误模式 + 下游模块依赖它
P1 = 0% 覆盖 + bug 难排查（如 descriptor 编解码）
P2 = 已有基础测试打底，补覆盖缺口
P3 = 大部分已覆盖，补边界/极端值
P4 = 跨模块集成，依赖单模块先稳定
6.4 不要做的事
反模式	为什么错
先写测试脚本再写 testplan	计划文件才是源头，代码是生成物
人手动更新状态	应该 Agent 写回，否则状态会过时
批量攒多个 case 再 commit	丢失粒度，无法追溯单个 case 的时间线
用 Excel/JIRA 替代 markdown	Git 无法 diff，Agent 需要额外 API
七、Git 审计示例
$ git log --oneline testplan.md

c6aad3c [V-05] ⬜ → ✅ | BF16 转换桥 bit-exact, 0 LSB error
b2d3e4f [V-02] ⬜ → ❌ | NaN 传播异常，需修复 add()
a1b2c3d [V-01] ⬜ → ✅ | FP32 add/mul 1000 组随机, max 0.7 ULP
9f8e7d6 [DM-01] ❌ → ✅ | 修复 decode 溢出，重测通过
8d7c6b5 [DM-01] ⬜ → ❌ | descriptor 往返失败，encode 字段顺序错误
每行 = 一个 case 的生死。不需要额外日志系统。

八、适用场景
场景	示例
硬件验证	NPU Func Model / RTL golden model 对比
编译器测试	指令编码/解码往返，优化正确性
量化精度	INT4/INT8/BF16 量化路径端到端
性能模型	理论峰值 vs 实测，瓶颈定位
协议实现	状态机覆盖，边界条件枚举
九、从零启动清单
 创建 testplan.md（用本模板）
 填写验收标准（每个模块定阈值）
 列出所有模块 → 标记已有测试覆盖 → 识别缺口
 按 P0→P4 排优先级
 收集规范文档（Agent 输入）
 检查 git 状态干净
 告诉 Agent：开始执行 P0
 人只需定期 git log --oneline testplan.md 看进展
