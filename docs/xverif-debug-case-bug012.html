1. 这是个什么 bug

BUG-RTL-SOC-012 是 SoC E2E 中 op05 attn_score MMUL 的 store-out 布局错误。

  • 算子维度：M=32, K=128, N=2
  • 预期：每行输出 2 个 INT32（8 字节），32 行在 SRAM 中紧密排列
  • 实际：行与行之间跨度 256 字节，cocotb 读回的数据只有 2/64 INT32 正确
仿真失败现场： First mismatch @ byte[8]: actual=0x00, golden=0xD0 — Total INT32 mismatches: 62/64

2. 传统 debug 痛点

  • 周期长： 加 $display、改 testbench、重新编译、重跑，每次十几分钟。
  • 信号难找： SoC 顶层信号多，APB/AXI 跨模块，手工点波形效率低。
  • 证据零散： log、wave、RTL 代码三头跑，难以把“寄存器配置”和“总线行为”关联起来。

3. xverif 是什么

xverif 是团队自研的验证工具链，通过 MCP server 暴露给 OpenCode / 脚本调用。它的核心能力是把 design hierarchy（daidir） 和 波形（FSDB） 绑定到一个 combined session，然后直接查询：

  • scope.list / scope.roots：快速浏览 elaborated hierarchy，定位实例和信号
  • value.at：在多个时间点批量采样信号值
  • axi.transaction.cursor / apb.query：协议级事务分析
  • trace.driver / trace.active_driver：静态/动态驱动追踪
关键优势： 不用开 Verdi GUI，不用写 Tcl/DO，直接通过结构化查询把“寄存器值 + AXI 地址 + 时间点”串成证据链。

在 xverif 可用之前，这个 bug 从 2026-08-31 首次暴露到 2026-09-03 根因确认，一共走了 6 轮有证据记录的迭代：

5. 环境准备：跑出一条带 FSDB 的用例

目标用例：run_e2e_attn_score（单 op05 MMUL）。要在 VCS 编译时打开 FSDB dump 并生成 Verdi KDB：

cd sim/regression
source /NAS/Tools/methodology/modules/init/bash
module load vcs/vcs_2023.12sp2 verdi/verdi_2023.12sp2

make VCS_OPTS="-full64 -sverilog -debug_access+all -kdb \
  -timescale=1ns/1ps +define+FSDB \
  -P /NAS/Tools/EDA/synopsys/verdi_V-2023.12-SP2_P/share/PLI/VCS/LINUX64/novas.tab" \
  run_e2e_attn_score

注意：Makefile 里 simv 从 repo parent 运行，所以 FSDB 会生成在 /home/prj/zhengs/caduceuscore/tb_soc.fsdb，而不是 repo 内部。

6. 打开 combined 会话

xverif MCP 配置在 .opencode/opencode.json。当前 OpenCode 会话若未重启，可通过 JSON-RPC 直调；正常流程是：

xverif_debug_session_open(
  name="bug012_demo",
  daidir=".../sim/regression/simv_soc_cocotb.daidir",
  fsdb=".../tb_soc.fsdb"
)

session 打开后，所有后续查询都基于同一个 combined context，设计层级和波形时间点一一对应。

7. 关键查询与波形证据

7.1 定位 hierarchy

用 scope.list 确认 MXU wrapper 实例路径：

tb_soc.u_dut.u_mxu_wrapper   mxu_soc_wrapper   module  true  false

7.2 查询 DIM1 寄存器

value.at tb_soc.u_dut.u_mxu_wrapper.dim1_n
2500ns  3000ns  3100ns  ...  3633ns
16'haa  16'h40  16'h40       16'h40

复位后 dim1_n 稳定在 0x40 = 64，而真实 N=2。

7.3 查询 AXI 写地址

value.at tb_soc.u_dut.u_mxu_wrapper.m_axi_awaddr
3140ns  3145ns  3150ns  3155ns  3160ns  3165ns
0x20020000 0x20020000 0x20020000 0x20020100 0x20020200 0x20020200
3170ns      3175ns      3180ns
0x20020300 0x20020400 0x20020500

每一行 store-out 的基地址递增 0x100 = 256 字节。

7.4 确认 burst 长度

信号值含义
m_axi_awlen0x34 beats / burst
m_axi_awsize0x664 bytes / beat
m_axi_wstrb0xffff_ffff_ffff_ffff64 字节 byte-enable 全有效

这意味着 wrapper 把每行当成 64 INT32 = 256 字节 来写，正好对应 0x100 的 stride。

8. 根因分析

MXU controller 用 dim1_n=64 计算输出 tile；wrapper 的 store-out FSM 也用这个 dim1_n 算行 stride，于是 SRAM 里每行之间空出 256B。而本次 MMUL 真实 N=2，期望的 dense stride 只有 8B。

SRAM 布局对比（每格 = 4 字节 INT32）
期望
0x20020000 row0 + row1 + row2 + ...
实际
0x20020000 row0 (2 valid INT32)
0x20020100 row1
0x20020200 row2
有效 INT32   未写入 / 读回为 0   cocotb 连续读 64B 时，row0 之后的 14 字节全是 gap，导致 62/64 mismatch。

9. Fix 方案与验证结果

台账里记录了两个 fix 方向，团队选择了低风险、与 firmware 语义一致的 driver-side fix：

  • 修改 sim/cocotb_bridge.py:2100-2107，去掉 engine_n = ((instr.dim_n + 63)//64)*64 的 pad-to-64。
  • 让 driver 直接把真实 N（本例为 2）写进 MXU DIM1。
  • wrapper 的 WRP_DIM_N 继续负责 store-out 的真实宽度控制。

修复后用同一个 run_e2e_attn_score 回归验证：

指标修复前修复后
dim1_n0x40 (64)0x0002 (2)
m_axi_awaddr 行 stride0x100 (256 B)0x08 (8 B)
INT32 mismatch62/640/64
test_e2e_attn_scoreFAILPASS
验证结论： DIM1 用真实 N 后，store-out 与 readback 的 dense 布局对齐，62/64 mismatch 消失。该改动仅影响 cocotb driver 路径，firmware 路径原本就写真实 N，因此不受影响。

10. 经验与建议

  • 先抓总线，再抓内部： AXI AWADDR 的 stride 直接暴露“行宽”假设，比追内部 FSM 更快。
  • 寄存器 + 波形联动： 同时看 dim1_n 和 m_axi_awaddr，一秒钟就能定位是“配置值错了”还是“配置对但行为错”。
  • 批量时间点查询： value.at 一次采样多个时间点，比 GUI 里来回拉 cursor 稳定得多，也方便落档。
  • 协议级动作更高效： 本次只用 value.at 已足够；复杂 AXI/APB 场景优先用 axi.transaction.cursor / apb.query。
  • 注意 FSDB 路径： 该项目的 simv 从 repo parent 启动，FSDB 生成在 ../tb_soc.fsdb，不要按惯性在 repo 内找。
  • MCP 需要重启加载： .opencode/opencode.json 修改后需要重启 OpenCode 才能在 skill_mcp 里直接调用；本次用 JSON-RPC 直调作为 workaround。
