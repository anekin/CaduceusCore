## Changes applied to sim/cocotb_bridge.py (test_e2e_intc_irq)

Extended test_e2e_intc_irq (previously only THRESHOLD=1 MXU path) with three
new scenarios, all exercised against rtl/intc/intc_top.v:159 semantics
(cpu_irq = |(PENDING&ENABLE) && popcount(PENDING&ENABLE) >= THRESHOLD):

1. THRESHOLD>1 popcount gating: 4 interrupt sources driven — MXU completion
   pulse (bit0), SFU completion pulse (bit1), Vector sticky status_done
   (bit2), TB-driven Timer level (bit6) -> PENDING=0x47, popcount=4.
   - THRESHOLD=5: cpu_irq stays 0 (4 < 5)
   - THRESHOLD=2: cpu_irq asserts (4 >= 2)
   - THRESHOLD=5 again: cpu_irq deasserts (1->0)
2. ENABLE=0 negative: THRESHOLD=1 + ENABLE=0x00 -> cpu_irq stays 0 while
   PENDING keeps 0x47 (mask gates cpu_irq, not PENDING).
3. ACK retention: ACK bit6 with timer level still high -> PENDING[6] re-sets
   next cycle (rtl/intc/intc_top.v:104 pending <= (pending & ~ack) | irq_src).

DEVIATION NOTE (documented in code + learnings): the plan prescribed
PENDING=0x55/ENABLE=0x55 (bits 0,2,4,6). Bit4 = pcie_irq, which is NOT
drivable from tb_soc (pcie_ep_wrapper.v: pcie_irq = irq_enable && irq_pending,
set only by an uncorrectable-error rising edge). The popcount-4 gate therefore
uses the four drivable sources (0x47 = mxu+sfu+vector+timer). Gating semantics
are identical to the prescribed 0x55 scenario and match the FM guard
sim/tests/test_intc_gating.py:109-117.

No RTL changes. rtl/intc/intc_top.v untouched. WFI wake-up NOT tested
(existing THRESHOLD=1 path already covers it).
