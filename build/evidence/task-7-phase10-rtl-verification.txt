## accumulator.v / mac_array Reset Signal Notes
  - accumulator.v reset_cmd port is tied to ext_acc_rst=0 in this SoC path.
  - The effective per-row accumulator reset is controller.mac_reset_acc -> mac_array.reset_acc,
    which clears all 64x64 local_acc registers (and pe_d1) on the cycle shown above.
  - Traces show mac_reset_acc rises exactly once per (M,N) tile group at k_tile=0,
    matching the RTL expression: mac_reset_acc = (k_tile==0 && !ctrl_acc_mode).
  - No difference in reset timing between M=1 and M=32.

## Divergence Analysis
  - Controller state, k_tile, mac_reset_acc, and CTRL[2] patterns are identical.
  - M=1 cos_sim=0.554298; M=32 cos_sim=0.019153. Both fail >=0.999 threshold.
  - The only firmware dispatch difference is act_offset = k_start * M:
      M=1:  k_start=64 => act_offset=64  (reads bytes 64..4160, wrong in tile-major)
      M=32: k_start=64 => act_offset=2048 (reads bytes 2048..6143, wrong in tile-major)
  - Tile-major layout places K-tile 1 at byte 4096; the current offset reads
    a mix of K-tile 0 tail and K-tile 1 head, corrupting the K-tile 1 partial sum.

## Verdict
  RTL control signals (CTRL[2], mac_reset_acc, state/k_tile/m_tile) are
  identical for M=1 and M=32, ruling out RTL accumulate/per-row-reset root cause.
  The firmware ring-buffer dispatch uses act_offset = k_start * M, which does
  not match the tile-major activation layout (K-tile stride = 64*64 bytes).
  This corrupts K-tile 1 activation fetch for every M>0; the effect is stronger
  for M=32 because the misaligned window contains a larger fraction of wrong data.
ROOT_CAUSE=FIRMWARE:ring-buffer dispatch uses act_offset=k_start*M instead of tile-major k_start*TILE_H, corrupting K-tile 1 activation fetch
